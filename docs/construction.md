## フェーズ概要

Construction フェーズは、Inception フェーズで定義した要件・設計を実際のコードに変換します。
各作業単位（Unit of Work）を独立して処理し、すべての単位が完了したら Build and Test で締めくくります。

### ステージ構成

```
作業単位ループ（各 Unit of Work に対して繰り返し）
├── Functional Design         （条件付き）
├── NFR Requirements          （条件付き）
├── NFR Design                （条件付き）
├── Infrastructure Design     （条件付き）
└── Code Generation           （常時実行）

Build and Test               （全単位完了後に常時実行）
```

{: .note }
> 重要：**1つの作業単位を完全に完了**（設計→コード生成まで）してから次の単位に移ります。

---

## Per-Unit Loop：作業単位ごとの処理

各作業単位に対して以下のステージが順番に実行されます。

### Functional Design（条件付き）

**実行条件：**
- 新しいデータモデルやスキーマが必要
- 複雑なビジネスロジックがある
- ビジネスルールの詳細設計が必要

**スキップ条件：**
- シンプルなロジック変更
- 新規ビジネスロジックなし

**生成内容：** ドメインモデル、データスキーマ、ビジネスルール、エンティティ関係図

完了後は **2択の承認メッセージ** が表示されます：
- `変更を要求する` — 修正してから次へ
- `承認して次のステージへ` — 次ステージに進む

---

### NFR Requirements（条件付き）

**NFR（Non-Functional Requirements、非機能要件）の評価**

**実行条件：**
- パフォーマンス要件がある
- セキュリティ上の考慮が必要
- スケーラビリティの懸念がある
- テクノロジースタックの選定が必要

**評価内容：**
- パフォーマンス目標（レイテンシ・スループット）
- セキュリティ要件
- スケーラビリティパターン
- 使用するテクノロジーの選定

---

### NFR Design（条件付き）

**実行条件：** NFR Requirements が実行された場合のみ

NFR Requirements で特定されたパターンを設計に組み込みます。
- キャッシュ戦略
- セキュリティパターン（認証・認可・暗号化）
- スケーリングパターン
- エラーハンドリング戦略

---

### Infrastructure Design（条件付き）

**実行条件：**
- インフラサービスのマッピングが必要
- デプロイアーキテクチャが必要
- クラウドリソースの仕様定義が必要

**生成内容：**
- クラウドサービスのマッピング（例：Lambda、DynamoDB、API Gateway）
- IaC（Infrastructure as Code）の仕様
- デプロイアーキテクチャ図

---

### Code Generation（常時実行）

すべての単位で**必ず実行**されるコア機能です。

#### 2段階のプロセス

**Part 1 — 計画**

AIが詳細なチェックボックス付き計画を作成します：

```markdown
## コード生成計画：[unit-name]

- [ ] src/api/users.py — User エンドポイントの実装
- [ ] src/models/user.py — User データモデル
- [ ] src/tests/test_users.py — ユニットテスト
- [ ] infra/dynamodb.tf — DynamoDB テーブル定義
```

**承認前に確認すること：**
- すべてのファイルが正しい場所にあるか（アプリコードは `aidlc-docs/` の外）
- 設計ドキュメントで定義したすべてが含まれているか
- brownfield の場合：既存ファイルを変更するのか新規作成するのか

**Part 2 — 生成**

承認済み計画を順次実行し、各ステップ完了時にチェックボックスを更新します。

{: .warning }
> **brownfield での注意**：`ClassName_modified.java` や `service_new.ts` のような重複ファイルが生成された場合は、すぐに以下を指示してください：
> ```
> [ClassName_modified.java] が [ClassName.java] と並んで生成されています。
> 変更を元のファイルにマージし、重複を削除してください。
> ```

---

## Build and Test（常時実行）

全作業単位のコード生成が完了した後に実行されます。

**生成される成果物（`aidlc-docs/construction/build-and-test/`）：**

| ファイル | 内容 |
|--------|------|
| `build-instructions.md` | 全単位のビルド手順 |
| `unit-test-instructions.md` | ユニットテスト実行手順 |
| `integration-test-instructions.md` | 統合テスト手順（単位間の連携テスト） |
| `performance-test-instructions.md` | パフォーマンステスト手順（該当する場合） |
| `build-and-test-summary.md` | 全体サマリー |

{: .tip }
> **テストフレームワークのタイミング**：テスト管理システムの指示はプロジェクト開始時ではなく、コード生成ステージで注入するのが効果的です。早期に注入すると、多くのステージを経て圧縮・消失することがあります。

## 設計ドリフトを防ぐ：Vibe Coding の禁止

### Vibe Coding とは

生成されたコードファイルを直接編集して素早く修正すること。短期的には速く見えますが、設計ドキュメントとコードが乖離し、後続の作業で一貫性が失われます。

### 正しい変更フロー

```
1. 問題を発見（コードを触らない）
   "問題 X を発見しました。コードは変更しないでください。
   設計を確認して、どこに対応が必要か理解してください。"

2. 設計ドキュメントを修正
   "[specific-design.md] を更新して [修正内容] を反映してください。
   上流ドキュメント（要件・ユーザーストーリー）も影響を確認してください。"

3. コードを再生成
   "[unit-name] の設計が更新されました。
   影響を受けるファイルのみ、コード生成を再実行してください。"
```

### 「ちょっとした修正」の場合も

1行の修正でも設計ドキュメントへの記録と合わせて行います：

```
[functional-design.md の unit X] で、[メソッド名] を [修正内容] に更新してください。
その後、影響を受けるファイルのコードを再生成してください。
```

---

## コード生成後の逆伝播

コード生成中に発生した小さな設計決定や調整は、完了後に設計ドキュメントへ反映させます：

```
コードのポリッシュが完了したら、各ユニットの最終設計ファイルを確認し、
変更を要件とユーザーストーリーまで逆伝播させてください。
実行する前にステップバイステップの計画を立ててください。
```

---

## 定義済みスタンディングルール（Construction 開始時に設定推奨）

Construction フェーズの開始時に以下の指示を設定することで、手動で確認する手間を省けます：

**全更新時の逆伝播チェック：**
```
ドキュメントを更新するたびに、要件ドキュメントとユーザーストーリーへの
影響を確認し、影響がある場合は私に知らせてください。
```

**コード生成時の設計優先ルール：**
```
コード生成中に設計決定を行う際は、コードに進む前に
必ずドキュメントに反映してください。
```
