## フェーズ概要

Inception フェーズは、開発を始める前に「何を・なぜ作るか」を明確にするフェーズです。
AIがビジネス意図を詳細な要件・ユーザーストーリー・設計に変換し、Construction フェーズへの入力を準備します。

### ステージ一覧

| ステージ | 実行条件 | 説明 |
|---------|---------|------|
| Workspace Detection | **常時実行** | brownfield/greenfield 判定 |
| Reverse Engineering | brownfieldのみ | 既存コードベースの解析 |
| Requirements Analysis | **常時実行**（深さ可変） | 要件定義 |
| User Stories | 条件付き | ユーザーストーリー生成 |
| Workflow Planning | **常時実行** | 実行計画の策定 |
| Application Design | 条件付き | コンポーネント設計 |
| Units Generation | 条件付き | 作業単位への分解 |

---

## 事前準備：インプットドキュメント

AI-DLCを最大限に活用するには、ワークフロー開始前に以下の2つのドキュメントを準備することを強く推奨します。

### ビジョンドキュメント（Vision Document）

何を作るか・なぜ作るかを記述します。

**最小限必要な内容：**
- 1段落：何を作るか・誰のためか
- MVP機能のリスト（スコープ内）
- 明示的に対象外とする機能リスト
- 既知の未決事項・オープンクエスチョン

### 技術環境ドキュメント（Technical Environment Document）

どのような技術スタックで作るかを記述します。

**最小限必要な内容：**
- 言語とバージョン
- パッケージマネージャ
- Webフレームワーク
- クラウドプロバイダとデプロイモデル
- テストフレームワーク
- **禁止ライブラリテーブル**（理由と代替案を含む）
- 典型的なエンドポイント・関数・テストのサンプルコード

{: .tip }
> **サンプルコードの価値**: 技術環境ドキュメントにサンプルコードを含めることが最も高レバレッジな追加です。AIはあなたのコードスタイルに従って生成できます。

詳細なテンプレートはリポジトリの `docs/writing-inputs/` にあります。

## Workspace Detection（常時実行）

**目的**：プロジェクトの状態を検出し、次に実行すべきステージを決定する

1. `aidlc-docs/aidlc-state.md` の存在確認（中断したセッションの再開）
2. ワークスペースの既存コードスキャン
3. **Brownfield**（既存コードあり）か **Greenfield**（新規）か判定
4. リバースエンジニアリング成果物の有無確認
5. `audit.md` に初期状態を記録
6. 次フェーズへ自動的に進む

---

## Reverse Engineering（brownfieldのみ）

**目的**：既存コードベースを解析し、後続フェーズの基盤を作る

既存コードがあり、リバースエンジニアリング成果物がない場合に実行されます。

**生成される成果物：**
- ビジネス概要（システムが実現するビジネストランザクションの説明）
- アーキテクチャドキュメント
- コード構造ドキュメント
- API ドキュメント
- コンポーネントインベントリ
- ビジネストランザクションの実装を示すインタラクション図
- テクノロジースタックドキュメント
- 依存関係ドキュメント

{: .warning }
> このステージは完了後にユーザーの**明示的な承認**が必要です。承認なしには次に進みません。

---

## Requirements Analysis（常時実行）

**目的**：ユーザーの要求を明確な要件に変換する

リクエストの明確さと複雑さに応じて3段階の深さで実行されます：

| 深さ | 適用場面 | 内容 |
|------|---------|------|
| **最小（Minimal）** | シンプルで明確なリクエスト | 意図分析のみ記録 |
| **標準（Standard）** | 通常の複雑さ | 機能・非機能要件の収集 |
| **包括（Comprehensive）** | 複雑・高リスク | 追跡可能な詳細要件 |

### 質問→ドキュメント→承認フロー

AI-DLCはチャットのインラインで質問しません。代わりに：

1. AIが `aidlc-docs/inception/requirements/requirement-verification-questions.md` に質問を書き出して待機
2. ユーザーがファイルを開いて `[Answer]:` タグに回答を入力
3. チャットに「回答を記入しました。ファイルを再読み込みして続けてください」と伝える
4. AIが回答を読み込んで検証し、次のステージへ進む

**回答の書き方のコツ：**

```markdown
## 質問：デプロイモデル

A) AWS Lambda（サーバーレス）
B) AWS ECS Fargate（コンテナ）
C) オンプレミス

[Answer]: B — ECS Fargate を選択。既存のコンテナインフラとの統合のため。
```

- **文字と説明を添える**: `B` だけより `B — ECS Fargate（コンテナインフラ統合のため）` が明確
- **複数選択も可**: `B と C — 両レイヤーでレート制限を実装`
- **X（その他）を活用**: 選択肢が合わない場合は X を選んで説明を記述

## User Stories（条件付き）

**目的**：開発チームが共通認識を持てるユーザーストーリーを生成する

### 実行される条件

**必ず実行：**
- 新規ユーザー向け機能・機能性
- ユーザーワークフローに影響する変更
- 複数のユーザータイプが関与
- カスタマー向けAPIの変更

**スキップされる条件：**
- ユーザーへの影響がゼロの純粋なリファクタリング
- 明確で独立したシンプルなバグ修正
- 機能変更なしのインフラ変更

### 2段階実行

1. **計画（Part 1）**: ストーリー計画を作成し質問を提示 → ユーザーが回答 → 曖昧さを解消 → **承認取得**
2. **生成（Part 2）**: 承認済みの計画を実行してストーリーとペルソナを生成

---

## Workflow Planning（常時実行）

**目的**：実行するフェーズと深さの計画を立て、ユーザーに提示する

1. 事前に収集したすべてのコンテキストを読み込む
2. 実行するフェーズと各フェーズの深さを決定
3. brownfieldの場合：複数パッケージの変更シーケンスを作成
4. ワークフロー可視化（Mermaid図）を生成
5. **ユーザーが計画を承認または変更できる** → ステージの包含/除外を指示可能
6. 承認後に実行開始

---

## Application Design（条件付き）

**実行条件：**
- 新しいコンポーネントやサービスが必要
- コンポーネントのメソッドとビジネスルールの定義が必要
- サービスレイヤーの設計が必要
- コンポーネント間の依存関係の明確化が必要

**スキップ条件：**
- 既存コンポーネント境界内の変更
- 新規コンポーネント・メソッドなし
- 純粋な実装変更

{: .note }
> **コンポーネントサイズ制約**：Application Design 時に「1コンポーネントのストーリーポイント上限」を設定することで、過大なコンポーネントを防止できます。

---

## Units Generation（条件付き）

**実行条件：**
- システムを複数の作業単位（Units of Work）に分解する必要がある
- 複数のサービス・モジュールが必要
- 複雑なシステムで構造化した分解が有効

**スキップ条件：**
- 単一のシンプルな作業単位
- 分解不要
- 単一コンポーネントのシンプルな実装

各作業単位は Construction フェーズで独立して処理されます（設計→コード生成まで完結させてから次の単位へ）。

---

## Inception → Construction への移行

すべての条件付きステージが完了し、Workflow Planning で承認を得た後、Construction フェーズに自動的に移行します。

Inception フェーズで生成されたすべての成果物が、Construction フェーズの各ステージで参照されます。
