## 基本ルール

### ドキュメントを変更せずに質問する

最初に身につけるべき習慣：**すべての質問がドキュメント更新を引き起こすわけではない**。

ガードなしで質問すると、AIが変更要求として解釈してすぐに設計ドキュメントを更新することがあります。探索的な質問には明示的な指示を付けます：

```
ドキュメントを更新しないでください。この [決定] が行われた理由を理解するのを助けてください。
```

```
何も変更しないでください。[提案する変更] の影響を評価してください。
決断する前に結果を理解したいです。
```

```
ドキュメントを更新しないでください。[コンポーネント名] で [ライブラリ名] を使うのは合理的ですか？
```

探索が完了したら、意図的な更新指示でフォローアップします。

## Question → Doc → Approval フロー

AI-DLC はチャットのインラインで質問しません。すべての質問をMarkdownファイルに書き出してユーザーの回答を待ちます。

### ステップ1：質問ファイルが作成される

```
aidlc-docs/inception/requirements/requirement-verification-questions.md
```

AIはこのファイルを作成して停止します。

### ステップ2：回答を記入する

ファイルを開いて各 `[Answer]:` タグに回答します：

```markdown
## 質問：デプロイモデル
このサービスはどこにデプロイしますか？

A) AWS Lambda（サーバーレス）
B) AWS ECS Fargate（コンテナ）
C) 既存のオンプレミスインフラ
X) その他（[Answer]: タグの後に記述）

[Answer]: B — ECS Fargate。既存のコンテナインフラとの統合のため。
```

**回答のコツ：**
- **文字+ラベルを添える** → `C` だけより `C — 財務サマリーと負債カバレッジ` が明確
- **根拠を書く** → `A — 設計優先。コード前にOpenAPI仕様を生成する` で意図が伝わる
- **複数選択もOK** → `B と C — APIゲートウェイとアプリケーションレイヤーの両方でレート制限`
- **例外を添える** → `B — ただし移行はスコープ外。新しいデータ構造への1回限りの移行を含める`
- **X は積極的に使う** → どの選択肢も合わない場合は X が正解

### ステップ3：AIに回答を知らせる

チャットに戻って：

```
回答を記入しました。ファイルを再読み込みして続けてください。
```

「**再読み込み**」を明示することで、AIがインメモリのキャッシュではなくディスクの最新内容を読み込みます。

### ステップ4：AIが検証して続行

AIが回答を読み込み、残っている曖昧さを報告してから次のステップへ進みます。

{: .tip }
> **事前ドキュメントを活用する**：「このドキュメントがすでに回答している質問は、自己解決してください。まだ不明な場合のみ質問してください」と指示することで、不要なやり取りを削減できます。

## コンテキスト管理

**AIの作業メモリ**（コンテキスト）を適切に管理することが最も高レバレッジな習慣の一つです。

### コアルール：各承認ポイントでコンテキストをリセットする

AI-DLC は**ゲート**（AIが止まって何かを聞く瞬間）を中心に構成されています。これらの一時停止は単なる承認チェックポイントではなく、**新しいコンテキストを開始する適切なタイミング**です。

ゲートでのリセットはリスクが低い：AIの現在の作業はすでにファイルに保存されているため。

コンテキストを複数のゲートにまたがって蓄積させると、AIは圧縮または部分的に失われた以前の指示や成果物から作業し始めます。品質低下が微妙で診断が難しくなります。

### 実践的な手順

- AIが質問ファイルへの回答を求めた → 回答記入後、**新しいコンテキストを開始**してAIに再読み込みを指示
- AIがドキュメントを承認のために提示した → レビュー後、**新しいコンテキストを開始**して変更要求または承認を行う
- ツールが「コンテキストを圧縮」を提案した → **常に断る**（圧縮はクリーンリセットではない）

### コンテキストリセット後の再開方法

**方法1：状態ファイル（推奨）**

```
aidlc-docs/aidlc-state.md を参照し、最初のチェックされていない項目を見つけて、
対応するプランファイルからその地点で再開してください。
```

**方法2：手動引き継ぎ**

```
以前の会話を再開しています。以下がコンテキストです：
[最後の出力または最近の変更のサマリーを貼り付け]
[次のアクション] を続けてください。
```

{: .tip }
> コンテキストリセット前に `git commit && git push` を実行すると、常にクリーンなリカバリポイントが確保されます。

## バッチプロンプトの使い方

**同じ主題に密接に関連した変更は1つのプロンプトに。関連しない変更は別々に。**

- 過度なバッチ（無関係な変更をまとめる） → AIが焦点を失い、詳細を見逃す
- 過少なバッチ（密接に関連したものを分ける） → 不必要な往復が増える
- 迷ったら分割する方向で

## 外部参照ファイルの読み込み

既存のドキュメント（スキーマ・アーキテクチャ図・データ辞書・API仕様）をAI-DLCの現在のステージに取り込めます：

```
[ファイルパスまたは説明] を読んでください。これを [目的] の基礎として使用してください。
```

```
既存の監査テーブル構造があります。これをInceptionドキュメントに追加して
このサービスで参照してください。進めるときに、このサービスに関連する
新しい要件とストーリーを期待してください。
```

## 独立したクリティーク

AI-DLC は自分が以前に作った設計決定を守ろうとします。偏りのない評価が必要な場合は、**新しいコンテキスト**でクリティークを依頼します：

```
[要件ドキュメント/コンポーネント設計] のクリティークドキュメントを作成してください。
他のすべてとは別の新しいコンテキストで行ってください。
```

同じセッションで作成されたものと同じセッションでクリティークを依頼するより、客観的なフィードバックが得られます。

## Inception フェーズの実践Tips

### ビジネス要件の明確化

```
現在の状態の説明と変えてはいけないものの明示的なリストを含む
brownfield用のビジョンドキュメントを準備してください。
```

### インラインデータソースを明示する

```
[サービス名] について、[新しいデータソース] が [既存データソース] に加えて
データソースであることを理解に追加してください。
その後、この点が要件とユーザーストーリーに反映されているか確認してください。
```

### 設計変更後の上流への影響確認

設計成果物に意味のある変更を加えた後：

```
前のステップ（ユーザーストーリーと要件）を確認して、
この変更がそれらのドキュメントの更新を必要としていないか確認してください。
```

### 機能の延期

```
現在のリリースでは [機能名] の機能をバックログに追加します。
コンポーネント設計から削除し、関連するユーザーストーリーをバックログ済みとしてマークしてください。
```

## Construction フェーズの実践Tips

### コード生成への移行時

```
コンポーネント設計レビューが完了しました。コード作成の準備ができています。
以下のディレクトリとソースコード構造を使用してください：
[既存のサービスまたはフォルダ構造を参照]
進める前に質問があれば聞いてください。
```

### 内部ライブラリの注入

コード生成計画を承認する前に：

```
私の回答に加えて、[スターターPJ/ビルディングブロック] から
以下のライブラリを使用する必要があります：[各ライブラリを明示]
何かを使用する理由とタイミングを、何かであるかだけでなく説明してください。
```

### テストカバレッジの範囲指定

```
ユニットテストを生成する際は、サードパーティの外部依存関係を
コードカバレッジ計算から除外してください。
内部コードパスのみで最低80%のカバレッジを要求してください。
```

## よくある落とし穴

### ❌ コードを直接編集する（Vibe Coding）

生成されたコードファイルに直接「ちょっとした修正」を加えることを避けてください。設計ドキュメントとコードが乖離し、次回のAI-DLC操作で不整合が発生します。

あるチームの言葉：
> 「コードを直接修正することはありません。問題を発見したら、AI-DLCに戻って言います：『問題Xを発見しました。設計を確認して修正の計画を立ててください。設計に影響する場合は更新してから、コードを更新してください。』」

### ❌ コンテキストを蓄積し続ける

複数の承認ゲートを超えてコンテキストを蓄積すると、品質が微妙に低下します。適切なタイミングでリセットします。

### ❌ レポートを `aidlc-docs/` に保存する

ステークホルダー向けのレポート・アーキテクチャ図は `aidlc-docs/` 内に保存しないでください。これらが設計成果物として読み込まれ、トークンを消費します。代わりに `reports/` フォルダを使用します。
